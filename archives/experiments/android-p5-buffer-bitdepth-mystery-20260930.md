# P5 8-bit vs 9/25 10-bit 缓冲之谜：判别实验与解答（2026-09-30）

## 结论

**「同解码器 9/25 曾输出 ~10-bit、现为 8-bit」的前提不成立：表面缓冲从未变成 8-bit。** 今日（398d0c3 修复后）设备 direct 路径的表面采样信号经主机管线结构性判别证实仍为 ~10-bit 精度；P5 修复记录中「华为硬解输出 8-bit NV12（AHB 0x325）」的机制归因是误判，但修复本身（dovi 元数据重标定 k=1023/1020）在正确与误判两种机制下数学等价、依然精确有效。

真实图景（合并 9/24-25 与今日全部证据）：

1. **缓冲不变**：`OMX.hisi.video.decoder.hevc` 对 Main10 的 surface 输出一直是 AHB `0x325`——9/25 格式对照已证 `0x30d`↔Main 8-bit、`0x325`↔Main10（`android-hevc-private-format-bitdepth-pair-20260925.md`），内容携带完整 10-bit 数据（8386 GL 读回对软解 99.7% 样本精确一致）。reader 参数（PRIVATE+GPU_SAMPLED_IMAGE、maxImages=3）、解码器名、格式号两代完全一致。
2. **签名不变**：驱动 `GL_EXT_YUV_target`（`__samplerExternal2DY2YEXT`）对该 10-bit 缓冲按 `/1020`（非 `/1023`）归一化——9/24 已证 `software_code = round(GPU_float×1020)` 且 code_scale=1020/1023 校正后 40 帧×120 值全部精确还原源码（`android-p5-code-scale-20260924.md`）。今日修复前的 `×1023/1020` 偏差签名与此完全相同。
3. **变化的是补偿的丢失**：9/25 sidecar shader 有 `code_scale=1020/1023` 修正；9/28 产品化重写 direct YUV 路径时丢失 → 0.29% 缩放回归。`398d0c3` 的元数据就地重标定（pivot×k、poly/MMR 按阶数 ×k^−d）是 `code_scale` 的精确数学等价（代入 s=s'/k），与缓冲位深解释无关地正确。

## 判别方法

用主机参照管线（/tmp/mkffdv ffmpeg n7.1.3 + libplacebo 7.360.1，滤镜串与 9/25 参照逐字节复现验证）构造两种 8-bit 量化模拟：`lutyuv` 确定性量化（round 或 floor 到 4 的倍数，无抖动、RPU side data 存活 `dovi=1`）后接同一 libplacebo dovi 管线，与设备 post-fix 整帧读回（12678 Sol f240、12679 4K50 f501）对比。判据：若设备表面信号是 8-bit，则设备↔量化模拟应降至噪声底（~12-25），且设备误差场与量化误差场强相关；若为 10-bit，则设备↔未量化参照低于量化噪声量级且相关≈0。

## 结果（/65535，MAE）

| 对比 | Sol f240 R/G/B | 4K50 f501 R/G/B |
| --- | --- | --- |
| 设备 ↔ 参照 sim10（未量化） | **47 / 51 / 71** | **51 / 20 / 59** |
| 量化噪声量级 sim8round↔sim10 | 119 / 71 / 72 | 92 / 71 / 73 |
| 设备 ↔ sim8round | 142 / 99 / 112 | 124 / 76 / 98 |
| 设备 ↔ sim8floor | 200 / 125 / 107 | 185 / 113 / 112 |
| corr(设备误差场, 量化误差场) | ≤0.03（两模型皆） | ≤0.003（两模型皆） |

设备对未量化参照的偏差在两个素材全部通道上**低于 8-bit 量化本身的噪声量级**（如 4K50 G：19.6 < 70.5），与两种量化模拟的 MAE 均劣于未量化参照，且误差场与量化模式零相关——8-bit 假设被拒绝。若设备为 8-bit（无论 round/floor、无论解码码值是否有亚 LSB 差异），其相对 F(c_sw) 的偏差不可能低于栅格约束误差；copy 路径 dump 的 `floor(c10/4)` 三平面 100% 精确匹配又强约束了解码码值与软解一致（同截断格内）。

## 对既有证据的重新解读

- **copy 路径 8-bit 是真的但不可外推**：mediacodec ByteBuffer 模式输出真 8-bit NV12（Y/U/V 全平面 100% 等于 `floor(c10/4)` 纯截断），但这是解码器的另一输出模式，与 surface 模式（0x325 10-bit）互不约束。P5 调查时以 copy 证据 + 缩放签名推定「表面缓冲也是 8-bit」，两步都不成立。
- **修复前数据本已含答案**：修复前设备对 `val×1023/1020` 模拟残差 R MAE 仅 33、均值 +4——量化噪声（~120）若存在不可能只剩 33，即修复前信号已是全精度 /1020 域。
- **P5 记录的「8-bit 均匀量化模型 (118,70,72) 不符」** 当时只用于排除系统性偏差成因，未上升为「残差中不含量化」的结构结论，本次以管线级模拟补齐。
- **残差来源修订**：post-fix 残差（Sol 47-71、4K50 20-59，偏置 ±7-37）**不是** 8-bit 量化，而是内容相关的其他差异（解码器与软解的亚 LSB 码值差、色度上采样细节等；4K50 G=19.6 已接近读回噪声底 12-17）。「恢复 10-bit 通路可把残差降到 (12,13,17)」的期望作废——通路本来就是 10-bit，无进一步修复空间，残差亦低于验收阈值。

## 边界

- 驱动为何按 /1020 归一化（0x325 的内部布局/栅格定义）未取得厂商证据；gralloc 静态核对（`android-p5-gralloc-0325-static-audit-20260925.md`）亦未定义。本结论只依赖「归一化分母=1020」这一经验事实，两代行为一致。
- 今日表面路径未直接做 10-bit 码值逐样本读回（9/25 的方法需重打 8386 式探针包）；本判别是管线输出级（三重独立证据：MAE 排序、量化噪声下限、零相关），未做逐码值验证。
- `398d0c3` 中 `0x325 = vendor NV12 … 8-bit` 的源码注释与 9/25 格式对照矛盾（0x325 为 Main10 关联格式），属注释性错误：重标定对 0x325（10-bit/1020 采样域）与 0x23/YV12（真 8-bit，码值 ×4/1020 域）两种情形都正确，行为无需改动；注释更正可随后续 mpv fork 提交顺带处理。
