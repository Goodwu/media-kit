# 4K60 SDR 掉帧归因：热状态主导、代码世代全排除（2026-10-02 凌晨）

## 结论

1. **掉帧数的巨大波动（335 ↔ 4808）由设备热状态主导，与代码无关**。决定性证据：9/30 保存的原始 12700 APK（字节不变）当时全片 VO 掉帧 **2102**，今夜复跑同包 **4808**（设备电池温度 41°C、GPU 被 capped 277MHz）；而 19 小时闲置后的真冷机上同代构建仅 **335**（GPU 可持续 586MHz 完赛，EOS/零解码丢弃）。
2. **所有代码世代在同等热状态下表现一致，无一可归因**：App 三代（合并前 96571a92 / 合并提交 a886f556 / 当前 main）× mpv 四代（c025cbf / 398d0c3 / 整改 5f9ddf1777）× libplacebo 两代（pre-fork / c9fd879）× Flutter SDK（全程 3.47.2 未变）——暖机状态全部 ~3300-4800。此前"App 侧归因"的初步判断（合并前 App 335 vs 合并后 3307）被暖机复测推翻（合并前 App 暖机同样 3372），系冷机首跑的伪差异。
3. **热-频率-掉帧链条**：真冷机 GPU 586MHz 持续 178s → 335 掉帧（3%）；中等热度（10min 冷却）586→277 过渡 → 1667-3307；连续运行（电池 41°C）GPU 直接钉 277/139MHz → 3300-4808（30-45%）。P8.4 轻路径在 277MHz 下零掉帧，证明 GPU 本身无恙，是 P5 direct 路径的渲染需求（586MHz 最大 boost）在热限制下不可持续。
4. **整改无负载回归**：同夜序列中整改版（3307 冷/3590 暖）不劣于 398d0c3（4750/4830）与 c025cbf（3805）；多格式回归 HDR10/P8.4 零掉帧不受影响。

## 未闭合残余（唯一）

9/28 历史轻负载记录（20-36 掉帧、GPU **持续 415MHz**）与今夜真冷机（335 掉帧、GPU **持续 586MHz**）之间的负载需求差异（415 vs 586）未闭合。候选解释：(a) P5 SDR 快速路径（`--dovi-p5-fast-path`，BT.1886 目标 + direct 路径时启用 gamut clip + downscaler NULL + `optimize_dovi_linear_decode`）在当前链（c9fd879 libplacebo 实现）上的实际降负载效益低于 9/28 实验包（当时 mkp4prefix 世代 libplacebo + P0 实验构建），或未实际 engage；(b) 设备 DVFS/热策略行为漂移。**验证方法已明确**：设备完全冷却后（电池 <35°C）跑当前产品 glass + mystery-sdr 各一轮，看 GPU 是否仍需求 586：若 415 → 快速路径效益健在、9/28 记录可复现；若 586 → 需查快速路径 engagement 与 c9fd879 的 optimize 实现。已排定时任务在清晨冷机执行。

**判定：冷机 GPU 需求为 586MHz（最大 boost），非 9/28 记录的持续 415MHz** → 9/28 轻负载未能复现，当前链的 P5 SDR 渲染负载需求确实高于 9/28 实验包世代。按预案登记下一步：**快速路径 engagement 验证与 c9fd879 `optimize_dovi_linear_decode` 实现对比**（9/28 轻负载来自 P0 实验包 + mkp4prefix 世代 libplacebo；候选方向为 auto 快速路径运行时未生效，或 c9fd879 的 optimize 实现效益低于旧实现）。本轮不展开调查。
